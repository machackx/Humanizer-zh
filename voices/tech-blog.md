# 默认声音档案：技术随笔

humanizer-zh 默认按本档案调整语气。档案描述一种口语化的中文技术随笔写法：短段落，逗号停顿，直接跟读者说话，用白话复述术语，中英文之间不加空格。

本档案依据用户提供的样本文章整理，只记录写法。仓库中不包含样本原文、样本里的经历或数据。下面的“例”都是另写的教学用句，不能写进目标文本。

## 优先级

1. 先遵守 SKILL.md 的第 1、2 条：保留事实、数字、条件、归因和确定程度，遵守用户的编辑范围。
2. 用户给了别的样本或风格要求，以用户的为准。
3. 用户说“保持原文语气”“不用默认风格”时，不使用本档案，按 SKILL.md 保留输入的语域。
4. 本档案的写法和原文意思冲突时，以原文意思为准。
5. 不要求每条都用上。按目标文本的需要挑着用，避免每段都堆满口头禅。

## 适用范围

| 文体 | 用到什么程度 |
|---|---|
| 个人经验分享、博客、技术观点长文、教程、工具和工作流介绍 | 全部适用 |
| 新闻快讯、产品发布报道 | 只用第 4 节的用词和第 7 节的标点；不加“我觉得”，不跟读者说话，不按一句一段拆分 |
| 正式商务文本、学术文本、法律文本、邮件和书信 | 不适用，保留原文语气 |
| 引语、代码、命令、表格数据、文件中的受保护内容 | 不受本档案影响 |

文件模式下，标题文字和层级按 SKILL.md 的文件保护规则保持原样，第 7 节关于标题的写法只用于粘贴文本。

## 1. 段落和节奏

- 一句一段：句号后换段，很多段只有一句。只调整分段，不为此改动句子本身；列表、表格和代码不拆。
- 一段之内可以用逗号把几层意思连成一长句。
  例：这个脚本每天跑一次，跑完会把结果写进日志，你第二天打开就能看到。
- 短句里用逗号停顿，放慢节奏。
  例：这一步，其实最容易出错。
- 冒号后换行，把结论或关键词单独放一行。
  例：这个问题的答案，其实很简单：（换行）先备份。
- 用一句话做开场或过渡。
  例：先说最核心的这块。／下面按顺序，一个一个说。

## 2. 句式

- 作者本来就在下判断的句子，可以用“我觉得”明说是自己的看法。这会让语气稍软；原文是事实陈述时不加。整篇一般一两处就够。
  例：我觉得这一步最值得花时间。
- 跟读者说话：“你会发现”“你可以想象”“你看，”“……对吧”。只用在原文本来就在给读者建议或提问的地方。
  例：如果你刚入门，建议先跑通最小的例子。
- 解释完再用白话说一遍：“翻译成人话就是”“大概意思就是”。只能复述原文已有的内容，不能借此补充新的解释。
- 原文已有比喻时，可以改成“这就跟……一样”的说法。不新增比喻。
- 列举用“比如……”。原文是完整列举时，不加“等等”。
- 列优点或步骤时，可以用“第一，……第二，……”。
- 否定对比可以用“不是……，是……”。只用于原文本来就有的对比，不新增假对比（SKILL.md §1）。
- 结尾可以用“……就行”“……就可以了”，但不能把“可以”“建议”加强成“只要……就够了”。

## 3. 连接词

高频：所以、其实、然后、并且、而且、基本、直接。

- “所以”常放段首，引出结论或下一步。原文没有因果关系时，不用“所以”连接两件事。
- “其实”用来引出解释或纠正误解，不要每段都加。
- “基本”“基本都”表示留有余地。原文说“全部”“一定”时，不改成“基本”；原文说“大部分”时，也不改成“全部”。

## 4. 用词对照

| 书面 | 口语 | 例 |
|---|---|---|
| 完成、处理 | 干、干完 | 让Agent把剩下的活干完 |
| 运行 | 跑 | 测试在本地跑一遍 |
| 构建、搭建 | 搭 | 先搭一个最小的版本 |
| 将……（处置） | 把…… | 把配置写进文件 |
| 例如 | 比如 | 比如超时和重试 |
| 如何 | 怎么 | 怎么恢复中断的任务 |
| 仅 | 只 | 只保留必要的字段 |
| 否则 | 不然 | 不然成本会涨上去 |
| 获得 | 拿到 | 拿到返回结果 |
| 方面 | 这块 | 部署这块 |
| 操作（电脑、浏览器） | 操控 | 操控浏览器 |
| 决策 | 拍板 | 需要人来拍板的事 |
| 以及 | 和、还有 | 日志、指标，还有告警 |

- 程度词：非常、特别、极、蛮、确实。程度跟原文的评价强度一致，不为了口语化而加码。
- 术语、产品名、版本号和 API 名称不换成口语词。“执行机制”“持久化”这类专业表达保持原样。

## 5. 数字

- 精确数据用阿拉伯数字；约数可以用汉字加“多、将近”。原文是精确数时，不改成约数。
- 给出数字后，可以换算成白话。
  例：从10分钟降到5分钟，少了一半。
- 换算只能用原文已有的数，结果要算对，不补新数据。

## 6. 术语

- 英文产品名、模型名和技术词照原样写。
- 原文给了定义时，可以用“大概意思就是”换成白话。原文没有给的定义，不要自己补；可以在正文外提醒作者补充。

## 7. 标点和格式

- 中文全角标点。
- 正文中，中文和英文、数字之间不加空格。
  例：LangGraph支持Python和TypeScript，一共3个节点。
- 英文词组内部、代码、行内代码和 URL 保持原样，如 Deep Agents、LangGraph v1。
- 引语用“”；文件名和口头说法用「」；书名、文章名用《》。
- 轻松的句子结尾可以少量用“～”。说明步骤、警告和正式结论里不用。
- 小标题可以用“1. ……”编号，最后一节可以叫“写在最后”。原文已有编号体系，且下面还有“1. 2.”这样的小项时，保留原编号，避免层级混淆。
- 少用粗体和破折号。整句加粗的论点可以去掉粗体；起小标题作用、方便跳读的粗体保留。

## 8. 语气

- 第一人称，谦虚，直接。原文有第一人称时保留并顺着写；没有时，不新增“我”的经历。
- 对不认同的做法可以直说，但语气强度不超过原文。
- 不加粗口和骂人的话。原文本来就有时，按原文保留。

## 9. 不要加入的内容

- 原文没有的经历、数据、案例、比喻和观点。
- 本档案里的任何示例句。
- 求点赞、在看、转发、星标之类的固定结尾，以及“希望对大家有用”这类收尾祝愿，除非用户明确要求。

## 10. 不模仿的写法

整理样本时发现几处可能是随手写法，默认不模仿。想保留时，把对应条目改写成上面的规则。

- 用“的”代替“地”“得”。
- 同一篇里货币单位混用。
- 同一名称前后写法不一致。
- 省略号写成“。。。”。
